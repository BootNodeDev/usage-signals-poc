# Decisions

One entry per technical choice: the decision, the source, the rejected alternative and why.
All sources were read on 2026-11-18. "Experiment" means it was run against the pinned images
in `docker-compose.yml` on that date.

## Platform

1. **Function form: one `export default { fetch(request) }` in `api/index.js`, routed by path, with a `/api/(.*)` rewrite.** Source: https://vercel.com/docs/functions/runtimes/node-js ("Avoid creating a separate function for each API endpoint", `fetch` Web Standard export). Rejected: `export default function handler(req, res)` (still documented as "Node.js helpers", not marked deprecated, but not the form the page leads with) and one file per endpoint (advised against).
2. **`vercel.json` is needed** for the rewrite above and for `Access-Control-Allow-Origin: *` plus immutable caching on `/s/*`. Sources: https://vercel.com/docs/project-configuration/vercel-json, https://vercel.com/docs/builds/configure-a-build ("Other" preset serves `public/` when it exists). Rejected: no config file; SRI on a cross-origin script fails without the CORS header.
3. **Node: `engines.node` is `>=24`, which Vercel resolves to 26.x, its default.** Source: https://vercel.com/docs/functions/runtimes/node-js/node-js-versions (available 26.x default, 24.x, 22.x). The suite passes on 24.22.1 and 26.12.1 locally. Rejected: pinning 24.x; nothing here needs the older line.
4. **Module format: native ESM through `"type": "module"`.** Source: https://vercel.com/docs/functions/runtimes/node-js (without it Vercel compiles ESM in `.js` to CommonJS). Rejected: `.mjs` for every file.
5. **Environment: values are read from `process.env` and fail with a message when missing; locally Node loads `local.env` with `--env-file`.** Sources: https://vercel.com/docs/environment-variables, https://nodejs.org/docs/latest-v24.x/api/cli.html (`--env-file`, `--env-file-if-exists`). Rejected: a dotenv dependency. Open: the file was meant to be `.env.example`; the session's permission settings deny writing `.env*` files, so it is `local.env`. Renaming it needs the two script lines in `package.json` and one line in the test changed.

## Database

6. **Client: `pg` 8.23.1 with a module-scope `Pool` registered through `attachDatabasePool` from `@vercel/functions` 3.11.3; idle timeout 5 s, `max` 5.** Sources: https://neon.com/docs/guides/vercel-connection-methods, https://neon.com/docs/connect/choose-connection, https://vercel.com/kb/guide/connection-pooling-with-functions. Rejected: `@neondatabase/serverless` (recommended only for platforms without pooling, and it does not talk to a plain local PostgreSQL over TCP). This makes two runtime dependencies, not one; `@vercel/functions` brings `@vercel/oidc` and its tree. Read in the package source: `attachDatabasePool` does nothing when `VERCEL_URL` is unset, so it is inert locally.
7. **Sources disagree on double pooling.** The Vercel guide above pairs a client-side `Pool` with `DATABASE_URL`, which the integration sets to the PgBouncer string; https://neon.com/docs/connect/choose-connection ("Common pitfalls") says to avoid client-side pooling on top of a pooled Neon connection. We follow the Vercel-specific guide. Not verified against Neon.
8. **Variable names: `DATABASE_URL` (pooled) for the function, `DATABASE_URL_UNPOOLED` (direct) for the seed's DDL.** Source for the Vercel-managed Marketplace integration: https://github.com/neondatabase/website/blob/main/content/docs/guides/vercel-managed-integration.md (table "Environment variables set by the integration"; the rendered page https://neon.com/docs/guides/vercel-managed-integration only says "`DATABASE_URL`, etc."). The Neon-managed variant documents the same two names: https://neon.com/docs/guides/neon-managed-vercel-integration. Rejected: `POSTGRES_*` (legacy) and `PG*` parts.
9. **PostgreSQL 18 locally.** Source: https://neon.com/docs/changelog/2026-06-05 and `pg_version` default 18 in https://neon.com/docs/reference/api/projects/create-project. Rejected: 17, as in the brief.
10. **Two applications, one database: Umami in `public`, ours in `usage_signals`, every statement schema-qualified, and no `?schema=` on Umami's URL.** Umami's documentation is silent on schemas (https://docs.umami.is/docs/install, https://docs.umami.is/docs/environment-variables). Its source reads a `schema` query parameter and then runs a session-level `SET search_path` before raw queries: https://github.com/umami-software/umami/blob/v3.5.0/src/lib/prisma.ts lines 757-759 and 868-877 (read and confirmed). Neon documents that a session `SET search_path` through its transaction-mode pooler carries over to other clients of the same role and database: https://neon.com/docs/connect/connection-pooling ("Common issues with SET statements"). Experiment: `?schema=umami` works on plain PostgreSQL; it was dropped for the reason above. Rejected: a second database (S2 asks for one).
11. **One database role, not a separate owner for our schema.** The research lead proposed a separate role. Not adopted: the integration injects credentials for one role only, and a second role means credentials managed by hand. Open for the product.
12. **Schema details.** Primary key of `api_metric_minute` leads with `(tenant_id, minute)`: https://www.postgresql.org/docs/current/indexes-multicolumn.html (equality on leading columns, range on the next). `ingest_token.token_hash` is `bytea`, 32 bytes, SHA-256 of a random token, plus `token_prefix`. https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html asks for at least 64 bits of entropy, not the 128 the lead quoted; the comment in `db/schema.sql` keeps 128 as the floor. That page does not state that a fast hash is sufficient for high-entropy tokens; that part is unsourced. No partitioning, no row-level security (S6).

## Gateway

13. **(Superseded by 33.) Visitor address, user agent and country reach Umami as `ip` and `userAgent` fields in the payload; the country is resolved by Umami from the truncated address.** Documentation is silent: https://docs.umami.is/docs/api/sending-stats lists neither field. Source: the 3.5.0 `/api/send` schema and `getClientInfo` in the image. Experiments: (a) payload fields: correct browser, OS, device and country; a location header sent alongside is ignored. (b) `x-forwarded-for` plus `User-Agent` headers: works on a bare Umami. (c) placeholder address plus a location header (`cf-ipcountry`): works, the header wins over the address. (b) and (c) were rejected because a hosted Umami sits behind a platform that overwrites `x-forwarded-for` (https://vercel.com/docs/headers/request-headers) and adds its own location headers, which describe the gateway, not the visitor.
14. **Refused fields: `ip`, `userAgent`, `timestamp`, `id`, `salt`, `browser`, `os`, `device`, at the root and in `payload`.** Source: every field the 3.5.0 handler reads to identify or date a visitor. The spec names the first four; the other four are the same class. Only `website`, `url`, `referrer`, `name`, `data` are forwarded; `hostname` is taken from the Origin.
15. **Client address: only `x-vercel-forwarded-for`, first entry.** Source: https://vercel.com/docs/headers/request-headers (Vercel overwrites `x-forwarded-for` to prevent spoofing; `x-vercel-forwarded-for` is identical and survives a proxy placed on top). https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For: only values added by a trusted proxy may be trusted. Rejected: `ipAddress()` from `@vercel/functions` (reads `x-real-ip`, same value, no gain). Locally there is no platform: `dev.mjs` plays that role and sets the header from the caller's `x-forwarded-for` or the socket, which is how the tests simulate visitors. That is not a trust decision, because `dev.mjs` is never deployed and the gateway code never reads `x-forwarded-for`.
16. **Truncation: IPv4 to /24, IPv6 to /48.** IPv4: https://www.cnil.fr/en/sheet-ndeg16-use-analytics-your-websites-and-applications ("truncate the last byte") and https://support.google.com/analytics/answer/2763052 (last octet; last 80 bits of IPv6). Open: Matomo's CNIL mode masks two bytes, so sources differ on IPv4; no regulator source was found for an IPv6 length, /48 comes from the architecture document and matches Google's 80 bits.
17. **CORS: the preflight and the 202 echo the Origin only when it is a registered domain of an active tenant, with `Vary: Origin`; no credentials.** Source: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Allow-Origin. The allowed request headers are the ones the 3.5.0 tracker sends (read in its source: `fetch`, `keepalive`, `credentials: "omit"`, JSON body, `x-umami-website-id`, `x-umami-hostname`, `x-umami-cache`). Rejected: a static rule in `vercel.json`, which cannot check an allowlist (https://vercel.com/kb/guide/how-to-enable-cors).
18. **Fail closed: 503 when the database or Umami cannot be reached or Umami answers 5xx; 400 when Umami rejects the payload.** No source; a design rule from the brief.

22. **Website id: accepted in any letter case and lower-cased before the lookup and before forwarding.** Source: https://www.rfc-editor.org/rfc/rfc9562 section 4 ("the alphabetic characters may be all uppercase, all lowercase, or mixed case"), so the three spellings are one UUID. Umami hashes the text it receives into the session id, so an upper-case id produced a second visitor. Rejected: refusing non-canonical ids, which would turn away input the RFC calls valid.
23. **Origin scheme: `https:` for every registered host; `http:` only when the host is loopback (`localhost`, `*.localhost`, `127.0.0.0/8`, `[::1]`).** Source: https://www.w3.org/TR/secure-contexts/ section 3.1 (those hosts are "potentially trustworthy" without TLS) and section 5.2. The architecture document says only that "the Origin matches one of its verified domains" and names no scheme, and `site.domain` stores none, so this rule is ours. Consequence, left as is: `https://localhost:4301` is accepted for the demo site served over http, because the registered value is a host, not an origin. Rejected: storing a scheme per site (a schema change for no gain in the prototype).
24. **A NUL character in `url`, `referrer`, `name` or anywhere in `data` is refused with 400.** No external source: PostgreSQL text cannot hold it, Umami 3.5.0 answers 500, and that would be reported as an outage. Only NUL is refused; other control characters are stored by Umami without error.
25. **Upstream status mapping: Umami 2xx gives 202; 400 or 422 gives 400; anything else (404, 429, 5xx, a timeout, no connection) gives 503.** Source: https://www.rfc-editor.org/rfc/rfc9110 sections 15.5.1, 15.6.3 to 15.6.5. RFC 9110 would allow the finer 502 for an invalid upstream answer and 504 for a timeout; one code is used because the caller's action is the same: retry later. Open: Umami answers 400 "Website not found" when a site exists in our table but not in Umami; that is a provisioning fault and is still reported as 400.
26. **Body cap of 16 KiB enforced while reading: a declared `Content-Length` over the cap is refused unread, and a streamed body is cancelled at the first chunk past the cap.** No external source. Locally `dev.mjs` buffers the request before the function sees it, so this is tested by calling the function with a streamed `Request`.

27. **The seed runs as the Vercel build command, set explicitly as `buildCommand` in `vercel.json` (`node scripts/seed.mjs`), with a `build` script of the same content.** Sources: https://vercel.com/docs/project-configuration/vercel-json (`buildCommand` overrides the project setting and the `build` script), https://vercel.com/docs/environment-variables ("Your source code can read these values to change behavior during the Build Step or during Function execution"), https://neon.com/docs/guides/vercel-managed-integration (migrations in the build command are Neon's documented pattern for this integration). Rejected: relying on the "Other" preset's default script name; https://vercel.com/docs/builds/configure-a-build does not state which npm script that preset runs, so the name is not left to it. With the "Other" preset the output directory is `public` when it exists, so files the build writes there are served. Not found in the documentation: any statement that database setup in the build is discouraged, or a better-supported hook for a no-framework project.
28. **Secret values in build logs.** Source: https://vercel.com/docs/environment-variables/sensitive-environment-variables (Vercel redacts Secret values of 32 characters or more from build logs). A shorter password is not redacted, so the seed never prints a variable's value and reports database failures by error code only; the driver's message can name the host.
29. **Seed profiles, chosen from Vercel's system variables.** Source: https://vercel.com/docs/environment-variables/system-environment-variables (`VERCEL`, `VERCEL_ENV` and `VERCEL_PROJECT_PRODUCTION_URL` are available at build and runtime; the last is "always set, even in preview deployments", has no scheme, and is the shortest production custom domain or the vercel.app domain). No `VERCEL`: the local fixtures. `VERCEL_ENV=production`: one tenant "Usage Signals demo" whose site domain is `VERCEL_PROJECT_PRODUCTION_URL`; a loopback or `.example` value stops the build. Any other Vercel environment: nothing is seeded, because preview builds may run against a database branch this project knows nothing about; the demo pages are still rendered and point at production, where a preview Origin is refused with 403. Consequence: adding a shorter custom domain later changes the registered domain at the next production build.
30. **`UMAMI_ADMIN_USER` defaults to `admin`.** Source: https://docs.umami.is/docs/install (the account Umami creates). 
31. **Demo pages are generated into `public/demo/` by the seed and are not committed.** The website id comes from the same profile object the seed writes to the database, and the tracker path and integrity from `public/s/manifest.json`, so the tag cannot drift from either. `src` and `data-host-url` are absolute (`https://<production host>`), which is the documented form of `data-host-url` (https://docs.umami.is/docs/tracker-configuration). Rejected: `data-host-url="/"`, which the 3.5.0 source would accept but the documentation does not show. Locally `dev.mjs` serves `public/` on the second port as well, so the same pages stay cross-origin there; `console/demo-site/` is removed.
32. **A same-origin `POST` from the tracker carries an `Origin` header, so the gateway needs no special case.** Source: https://fetch.spec.whatwg.org/#append-a-request-origin-header : the header is appended for every request whose method is neither `GET` nor `HEAD`; the referrer-policy cases that turn it into `null` apply only "if request's mode is not cors", and the tracker calls `fetch()`, whose default mode is `cors`. What would break it: a page that posts with a form or `no-cors` under `Referrer-Policy: no-referrer` sends `Origin: null`, which the gateway refuses with 403. The Origin check is unchanged.

33. **Supersedes 13. The visitor's truncated address goes to Umami in the `cf-connecting-ip` header and the country in `cf-ipcountry`; `ip` is no longer sent in the payload. `userAgent` stays in the payload.** Root cause of the production failure, all at tag v3.5.0: `umami/scripts/build-geo.js:14-17` skips the GeoLite2 download when `VERCEL` is set and `BUILD_GEO` is not, so a Vercel-hosted Umami has no `geo/GeoLite2-City.mmdb`; `umami/src/lib/detect.ts:139` calls `getLocation(ip, headers, !!payload?.ip)`, so a payload `ip` skips the location headers (`detect.ts:95`) and reaches `maxmind.open` (`detect.ts:113-118`), which throws ENOENT, answered as 500. Reproduced locally with the `umami-nogeo` service (`GEOLITE_DB_PATH` pointing nowhere, `detect.ts:117`): the old request got 500, the new one 200.
    - Headers Umami reads, in order: address from `true-client-ip`, `cf-connecting-ip`, `fastly-client-ip`, `x-nf-client-connection-ip`, `do-connecting-ip`, `x-real-ip`, `x-appengine-user-ip`, `x-forwarded-for`, ... (`umami/src/lib/ip.ts:3-17`, first present wins, `ip.ts:179-205`; `CLIENT_IP_HEADER` overrides, `ip.ts:180-184`); country from `cf-ipcountry`, then `x-vercel-ip-country`, `cloudfront-viewer-country`, `eo-ipcountry` (`umami/src/lib/detect.ts:12-47`, loop at `detect.ts:96-109`). `x-umami-client-ip` and `x-umami-client-country` exist only with `CLOUD_MODE`.
    - Why this pair: Vercel documents that it overwrites `x-forwarded-for` and that `x-real-ip` is identical to it (https://vercel.com/docs/headers/request-headers), so those two would carry the console function's own address at Umami; `cf-connecting-ip` and `cf-ipcountry` both come earlier in Umami's lists than anything Vercel sets. **Not documented and unverified until deployed: that Vercel's edge passes caller-set `cf-connecting-ip` and `cf-ipcountry` through to the Umami function.**
    - Country source: the gateway reads `x-vercel-ip-country`, which Vercel sets from the requester's public address (same page). Only a two-letter upper-case value is relayed. No geo database is used anywhere on Vercel. Locally `dev.mjs` passes the caller's `x-vercel-ip-country` through, which is how the tests supply it; a local browser sends none and the local Umami then falls back to its own database.
    - Visitor identity: Umami derives the session id as `uuid(sourceId, ip, userAgent, sessionSalt, distinctId)` (`umami/src/lib/collection-session.ts:111`), with the monthly salt by default (`umami/src/lib/crypto.ts:88-101`). The header carries each visitor's truncated address, so two visitors behind the platform are two sessions and one visitor on two pages is one, with Umami's rotation unchanged. Rejected for the per-visitor value: `payload.id`, which is stored as `distinct_id` and marks the session as identified (`umami/src/app/api/send/route.ts:107`), and `payload.salt`, which is ignored unless `ENABLE_CLIENT_SALT` is set on the Umami project (`collection-session.ts:109`). Both stay on the refused list.
    - Difference from the architecture document: it sends a fixed placeholder address and a per-visitor salt; here the truncated address itself is the header value, as in T1. A placeholder cannot be a reserved address, because Umami returns no location for local or invalid addresses before it looks at any header (`detect.ts:90-93`).
    - **Fallback, no code change in the gateway beyond reverting this entry:** set the documented build-time variable `BUILD_GEO=1` on the Umami project (https://docs.umami.is/docs/environment-variables, read by `build-geo.js:14`), so the build downloads the database, and keep `ip` in the payload. Unverified: that the file ends up in the function bundle on Vercel.
    - Limit: when Vercel gives the gateway no country, no `cf-ipcountry` is sent and a Vercel-hosted Umami falls through to its own `x-vercel-ip-country`, which describes the console function, not the visitor.
    - Open: whether a caller can supply its own `x-vercel-ip-country` to the gateway. The page above describes it as set by Vercel but does not say caller values are discarded. The worst case is a caller misreporting its own country.

## Known limits

- `screen`, `language`, `title` and `tag` are not forwarded, so there is no laptop/desktop split and no page titles.
- Requests without a JSON `Content-Type` are accepted, because the Origin check still applies.

## Tracker

19. **The tracker is Umami's own file with its documented `COLLECT_API_ENDPOINT` rewrite, plus `data-host-url` on the tag.** Sources: https://docs.umami.is/docs/environment-variables (`COLLECT_API_ENDPOINT`), https://docs.umami.is/docs/tracker-configuration (`data-host-url`). Both are needed: the rewrite changes the path, and without `data-host-url` the tracker posts relative to its own directory. No source edit.
20. **SRI with `sha384` and `crossorigin="anonymous"`; the file is served with `Access-Control-Allow-Origin: *`.** Source: https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Subresource_Integrity. Rejected: `sha512` (allowed, no practical gain) and a tag without `crossorigin` (the browser would refuse the integrity check).

## Tests

21. **`node:test` with `describe`/`it`, run as `node --test "test/*.test.mjs"`.** Source: https://nodejs.org/docs/latest-v24.x/api/test.html. `node --test poc/test/` does not work: Node 24 treats the directory as a module path.

## What the Umami deployment needs

- `DATABASE_URL`: the pooled Neon string, with no `?schema=` (decision 10). `DIRECT_DATABASE_URL`: the unpooled string, used for migrations since v3.2.0. `APP_SECRET`: required since v3.5.0, `openssl rand -hex 32`. Source: https://docs.umami.is/docs/guides/running-on-vercel, https://docs.umami.is/docs/environment-variables.
- It can share the Neon database with this project: Umami in `public`, ours in `usage_signals`. Verified on local PostgreSQL 18, not on Neon.
- Change the default `admin` / `umami` password at once; that deployment is public. The seed then needs `UMAMI_ADMIN_PASSWORD` set to the new value.
- Umami's docs ask for Node 20.19 or newer and recommend 22; Vercel's default is 26.x. Umami on 26 is unverified: set that project to 22.x.
- Open: Umami's own `/api/send` stays publicly reachable there, so the gateway can be bypassed. Accepted for the prototype (see the task document header).

## Later (T3, not built)

- `http.server.request.duration` is in seconds, advisory bounds 0.005 to 10. OTLP JSON encodes 64-bit integers as strings and enums as integers. Unsupported data points are answered with HTTP 200 and `partialSuccess.rejectedDataPoints`; 400 only for undecodable bodies. Source given by the research pass: https://opentelemetry.io/docs/specs/otlp/ (not re-read here).
